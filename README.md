## 이 포트폴리오를 관통하는 한 가지

프로젝트 7개 중 **5개가 1~3년 전 과제를 다시 열어 제 결론을 직접 검증한 기록**입니다.
단순히 다시 돌려본 것이 아니라, **당시의 결론이 데이터에서 성립하는지 다시 재고**
성립하지 않으면 그 사실과 원인을 남겼습니다.

그 과정에서 찾은 것들입니다.

| 프로젝트 | 당시 믿었던 것 | 다시 재어본 결과 |
|---|---|---|
| 뇌졸중 예측 | "정확도 94~96%" | **환자를 0명 검출**하는 모델의 수치였음 (발병률 4.87%) |
| 연봉 예측 | "리키지 변수라 제외했다" | 리키지가 아니라 **중복 변수**였음 |
| 와인 품질 | 보고서 결론 3건 | **13건 중 12건**이 데이터에서 성립하지 않음 |
| 표정 분류 CNN | "데이터셋 22,968장" | **버그로 5,700장씩 버려진 뒤**의 숫자였음 |
| 분산 DB | "보안 6계층 적용" | 전부 네트워크 계층. **앱에는 로그인 자체가 없었음** |

전부 **에러 없이 잘 돌던 코드**에서 나왔습니다. 그래서 이 포트폴리오가 보여주려는 것은
"돌아가는 코드를 썼다"가 아니라 **"돌아가는 코드를 의심하고 다시 쟀다"** 입니다.

나머지 2개는 그 태도를 **과거가 아니라 지금 하는 작업에** 적용한 기록입니다 —
하나는 분석을 **실제로 쓸 수 있는 서비스로** 만든 것이고,
다른 하나는 **"개선인지 잡음인지"를 판정하는 기준부터 세우고** 시작한 Kaggle 과제입니다.

## 프로젝트 상세

### 1. 표정 분류 CNN → 이모지 매칭

사진 속 표정을 읽어 어울리는 이모지를 찾아주는 파이프라인입니다. 2023년에 1단계(CNN)만
완성하고 3단계에서 막힌 채 끝났던 과제를, 3년 뒤 다시 열어 끝까지 완성했습니다.

- **데이터 손실 버그 발견·복구** — `validation_split`이 `train/`과 `test/` **양쪽에** 걸려
  약 5,700장씩 조용히 버려지고 있었습니다. 버그를 그대로 둔 **Run A(0.5720)** 와 고친
  **Run B(0.5954)** 를 같은 전체 test(7,178장)로 평가해 **손해액을 +4.1%로 확정**했습니다.
- **3년 만의 혼동행렬** — 전체 정확도 하나로만 알던 모델을 클래스별로 쪼개니, 표본이 가장
  적은 `disgusted`(111장)가 성능도 가장 낮았습니다(F1 0.351). 표본 부족이 실제 손해로
  이어진다는 것을 수치로 확인했습니다.
- **3단계는 모델이 필요 없었습니다** — CNN을 이모지에 돌리려던 접근이 막혀 있었는데,
  필요한 감정 레이블이 `emoji_df.csv`의 `name` 칸에 **이미 있었습니다**. 가장 비싼 해법부터
  떠올린 것이 3년간 막힌 진짜 원인이었습니다.
- **외부 기준과 비교** — 같은 100장을 제로샷 LLM 비전 모델에 돌려 0.650 대 0.750으로
  비교했습니다. "무작위의 3.9배"는 하한선과의 비교일 뿐이었습니다.

> **다음 단계(예정)** — scratch 학습의 상한이 0.5954라고 보고, Hugging Face의 표정 분류
> 사전학습 모델을 **파인튜닝**해 같은 전체 test(7,178장) 기준으로 비교할 계획입니다.
> 아직 실행하지 않았으므로 위 수치는 전부 기존 CNN의 것입니다.

### 2. Photo2Emoji 서비스

위 파이프라인이 노트북 안에서만 돌던 것을 **FastAPI 서비스**로 만들었습니다.

- `POST /predict` — 사진 업로드 → 확률 벡터·클래스·확신도·이모지 JSON 응답
- **pytest 10개 통과**, venv·Docker 컨테이너 **양쪽에서 실측 응답 확인**
- 매칭 규칙은 다시 짜지 않고 **노트북 로직을 그대로** 옮겼습니다 — 서비스 쪽에서 "개선"하면
  노트북의 검증 결과가 더 이상 그 서비스를 설명하지 못하기 때문입니다. 두 쪽이 갈라지지
  않도록 매핑표 개수를 단언하는 테스트로 묶어뒀습니다.
- **정확한 예측 클래스는 테스트에서 단정하지 않았습니다** — 정확도 0.5954인 모델에
  그런 테스트를 걸면 모델을 조금만 손봐도 깨집니다. 테스트 대상은 모델 성능이 아니라
  서비스의 규약이어야 했습니다.

### 3. 분산 DB 회의실 예약 시스템

MongoDB Replica Set 위에 Flask 앱을 올린 회의실 예약 시스템입니다. 물리 PC 2대 환경이
사라져 재현할 수 없던 것을 **Docker 3노드로 다시 돌려 검증**했습니다.

- **Failover 실측** — pc1 강제 종료 후 **약 10초 만에 pc2가 Primary로 승격**, 재시작 후
  정상 재합류까지 확인. 데이터 노드가 2개면 과반수 규칙 때문에 오히려 failover가 안 되고,
  투표권만 갖는 Arbiter 하나가 가용성을 만드는 구조입니다.
- **보안 감사 2회** — 1차에서 **인증 자체가 없다는 것**을 발견했습니다(`password_hash`는
  저장만 되고 검증하는 로그인 라우트가 없었음). 5건 패치 후, 2차에서 **패치된 코드를 다시
  감사해 13건을 추가 발견**하고 심각도 '높음' 3건을 수정했습니다 — 오픈 리다이렉트,
  예약 IDOR, 빈 비밀번호 계정. 전부 mongomock으로 재현하고 패치 후 결과가 뒤집히는 것까지
  확인했습니다.
- **남은 10건은 미조치입니다.** 문서에 그대로 적어뒀습니다 — 이 프로젝트는 "보안 점검 완료"
  상태가 아닙니다.
- Docker로 **검증할 수 없는 것**(Tailscale 전송 암호화, ufw, ACL)은 따로 목록으로 분리했습니다.

> 공개 범위는 문서입니다(README 2개 + 보안 감사 보고서). 인프라 설정과 애플리케이션 코드는
> 저장소에 포함하지 않습니다.

### 4. 와인 품질 회귀분석

이화학 성분으로 관능 평가 점수를 설명할 수 있는지 본 팀 과제입니다. 재검증을 시작하고 나서야
**과제가 서로 다른 두 트랙으로 진행됐다는 것**을 알게 됐습니다.

- **1부(적포도주 OLS)** — "가장 큰 영향"으로 지목한 `density`는 **단위 착시**였습니다.
  표준편차가 0.0019라 계수만 커 보였고, 표준화하면 11개 중 10위에 p=0.409로 유의하지도
  않았습니다. 핵심 이슈로 든 고상관은 **백포도주 값**이었고, R²=1.0은 `quality`가 특성에
  들어간 **타깃 누수**였습니다. 중복 240행이 RandomForest만 0.129 부풀리고 있었습니다.
- **2부(백+적 병합 ML)** — 자랑하던 **RandomForest R² 0.712는 업샘플링을 분할 전에 수행한
  누수**였습니다. 테스트의 59.6%가 훈련에 쌍둥이를 갖고 있었고, 순서만 바로잡으면 **0.548**
  입니다. 변환 비교 40여 셀은 변환 함수가 **타겟까지 변환**해 비교 자체가 불가능했습니다.
- 한 달 뒤에야 2부 노트북이 재검증 범위 밖이었다는 걸 알았습니다. **"최종"이라는 파일명이
  그 파일을 봤다는 뜻은 아니었습니다.**

### 5. 뇌졸중 발병 예측

- **"정확도 94~96%"의 정체** — 발병률이 4.87%라 "전원 비발병"이라고만 답해도 95.13%가
  나옵니다. 실제로 실험 노트북 3개가 환자를 **0명 검출**하면서 그 정확도를 기록하고 있었습니다.
- **"결측값 43%"는 분모를 잘못 잡은 값**이었고(올바른 값 30.2%), 그 숫자가 1,544행 삭제의
  근거였습니다. 게다가 `bmi` 결측은 무작위가 아니라(χ² p<1e-6) **결측군 발병률이 19.9%**
  (비결측군 4.26%)여서, 삭제하면 가장 위험한 환자를 선별적으로 버리게 됩니다.
- PR-AUC를 주 지표로 재구축 — **0.225±0.043**(무작위 기준선 0.049), 재현율 0.787.
  **나이 하나가 전체 모델 성능의 78%**를 설명하고(0.175 vs 0.225), 나머지 변수 10개가
  더하는 실질 가치는 PR-AUC 0.05 정도였습니다.

### 6. 데이터 직무 연봉 예측

문서에 *"`salary_currency`는 리키지라서 제외했다"* 고 적어뒀는데, **코드는 그 컬럼을 계속
쓰고 있었고** 확인해보니 **리키지도 아니었습니다.** 통화별 환산비가 상수라 `salary`와
**함께** 쓸 때만 누수이고, 단독으로는 `company_location`과 겹치는 중복 변수였습니다
(USD 하나가 32개국에 걸침).

회귀로 재프레이밍하고 기준선부터 쌓아 올려(전체 평균 → 조회 테이블 → Ridge → RandomForest)
각 단계의 기여를 측정했습니다 — 채택 모델 **Ridge + `log1p`, R² 0.500±0.069 (MAPE 42.6%)**.

### 7. 항공사 승객 만족도 예측 ([별도 저장소 ↗](https://github.com/jongchacha16-jpg/airline-satisfaction-prediction))

Kaggle Playground Series S6E10. 이미 OOF AUC **0.95866**인 베이스라인이 있었고 목표는
**0.9600** 돌파 — 남은 여지가 0.0013이었습니다.

그런데 재보니 **Fold별 AUC의 표준편차가 0.00058**이었습니다. **잡음과 목표 개선폭의
자릿수가 같았습니다.** 그래서 이 과제의 어려운 부분은 모델을 더 좋게 만드는 일이 아니라
**"지금 올라간 0.0005가 진짜 개선인가, 운인가"를 판정하는 일**이었습니다.

- **성능을 재기 전에 판정 기준부터 적었습니다** — *"Pooled OOF 개선 且 5개 Fold 중 4개
  이상에서 개선일 때만 채택"*. Fold 분할을 모든 노트북이 공유하도록 고정하고 첫 셀에서
  행별 일치를 `assert`합니다. 기준을 나중에 만들면 그건 측정이 아니라 합리화입니다.
- **런타임 오인 하나가 전략을 뒤집었습니다** — 노트북 **전체** 1,205초를 LightGBM **학습**
  시간으로 읽고 있었습니다. 실측 **40초**. *"Optuna는 16시간이라 불가능"* 이라는 판단이
  무너지면서 결과적으로 **가장 큰 기여를 한 단계**가 열렸습니다.
- **가장 유망하다고 본 피처가 기각됐습니다** — EDA에서 0점 역전이 뚜렷했지만(만족률 88%),
  LightGBM이 `<= 0.5` 분기로 **이미 자력 분리**하고 있었습니다. 설계한 피처 4개 중
  **3개를 기각**했습니다.
- **대조군도 동등하게 대우했습니다** — Optuna 결과를 3시드 평균 낼 때 챔피언도 같은
  3시드로 재측정했습니다. 안 했다면 이득이 **17% 부풀려졌을** 것입니다.
- **앙상블 다양성은 Spearman으로 판정** — Pearson으로는 전 모델이 0.99 이상 "동일"하지만,
  ROC-AUC는 **순위만** 봅니다. CatBoost는 XGBoost와 다양성이 같은데 7.5배 비싸 기각했습니다.

**최종 OOF 0.95994 (+0.00128).** 목표에 **0.00006 미달**했고, 세 단계 중 **튜닝만이 확실히
유효**했습니다. 최종 +0.00008이 MLP의 낙관 편향에 일부 기대고 있을 가능성도 문서에
적어뒀습니다.

> **다음 단계(예정)** — 제출은 끝났지만 피처·앙상블 양쪽에서 여지가 소진된 상태라,
> **아키텍처를 수정해** AUC를 더 올려볼 계획입니다. 판정 기준(Fold 계약·4/5 Fold 규칙·
> 대조군 동등 처리)은 그대로 유지합니다 — 기준을 바꾸면 이전 단계들과 비교가 성립하지
> 않습니다.

> 이 프로젝트에서 가장 많이 한 일은 추가가 아니라 **기각**이었습니다 — 피처 3개, CatBoost,
> rank 변환. 각각 "왜 안 되는지"의 근거가 남았고, 그쪽이 재사용 가능한 자산이라고 봅니다.

## 한계 (정직하게)

- **7개 중 5개가 과거 수업 과제의 사후 분석**입니다. 2·7번만 현재 진행형 작업이고,
  처음부터 문제를 정의해 데이터를 모은 프로젝트는 아직 없습니다.
- 데이터가 전부 **공개 데이터셋(Kaggle/UCI/COCO)** 입니다. 크롤링·API 수집 경험은
  포트폴리오에 없습니다 — 7번을 추가한 뒤에도 이 한계는 그대로입니다.
- **SQL 기반 분석 프로젝트가 없습니다.** 분산 DB 프로젝트의 MongoDB가 유일한 DB 경험입니다.
- 재검증 계열 프로젝트의 성능 수치는 높지 않습니다(CNN 0.5954, 와인 R² 0.342, 연봉 R² 0.500).
  **왜 그 수준이 상한인지**를 데이터 구조로 설명하는 데 무게를 뒀습니다.
- 7번은 목표(AUC 0.9600)에 **0.00006 미달**했습니다. 세 단계 중 튜닝만 확실히 유효했고,
  나머지 두 단계는 여지가 소진됐다는 것이 결론입니다.
