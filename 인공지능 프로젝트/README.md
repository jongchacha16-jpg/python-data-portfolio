# 사진 → 감정 → 이모지 매칭 (Photo-to-Emoji)

**사진 속 인물의 표정을 읽어 그 사람에게 맞는 이모지를 찾아주는 것**이 이 프로젝트의 목표입니다.

원래 구상은 사진으로 **나만의 이모티콘을 생성**하는 모델이었으나, 학습 데이터의 한계를 확인하고
**기존 이모지 중에서 골라주는 방식**으로 범위를 좁혔습니다. 이 판단은 옳았습니다 —
사진에서 *새로운* 이모지를 만들려면 (사진, 대응 이모지) 쌍 데이터가 대량으로 필요한데 그런 데이터셋은 없습니다.

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| 0 | 사진 → **나만의 이모티콘 생성** | 데이터 한계로 축소 (아래 1~3으로 대체) |
| 1 | 사진 → **표정 분류** (7개 감정) | ✅ CNN 학습 완료 (검증 정확도 0.5628) / ⚠️ 가중치 소실 |
| 2 | 분류 결과 → **감정 수치화** | ✅ 1단계 softmax 출력이 곧 그것 — 이미 있었습니다 |
| 3 | 수치 → **대응 이모지 할당** | ✅ **완성** (`이모지_매칭_파이프라인.ipynb`) |

3단계는 2023년 당시 막혀 있었고, **2026-09-10에 완성했습니다.**
1단계 가중치만 복구하면 사진을 넣어 이모지가 나오는 완결된 파이프라인이 됩니다.

> **⚠️ 이 README는 2026-09-07에 정정되었습니다.**
> 이전 README는 이 프로젝트를 *"기한 내 목표를 완전히 달성하지 못했다 / 모델 학습까지 완료하지 못했다"*

> 실패한 것은 부가 시도였던 이모지 변환 하나였고, 그 실패 원인 진단도 틀렸습니다(아래 §실패한 부분 참고).

>
> | 디렉터리 | 지정한 subset | 실제로 쓴 비율 | 결과 |
> | --- | --- | --- | --- |
> | `train/` | `training` | 80% | 나머지 **20%(약 5,700장)를 학습에 쓰지 않음** |
> | `test/` | `validation` | 20% | 나머지 **80%(약 5,700장)를 평가에 쓰지 않음** |
>
> 원래 의도는 `train/` 전체로 학습하고 `test/` 전체로 검증하는 것이었을 텐데,
> 양쪽에서 각각 약 5,700장씩 버려졌습니다.
>
> **버그 자체는 코드에서 확정**이지만, 버려진 정확한 장수는 데이터셋을 다시 확보해야 확정됩니다.
> (역산하면 `train/` ≈ 28,710 / `test/` ≈ 7,160이고 이는 FER2013 규모와 맞지만,
> 이 Kaggle 배포본은 정본과 클래스별 장수가 조금 다릅니다 — 정본 기준 계산과 ±3~7장 어긋납니다.)
>
> → 재학습 결과는 아래 [재학습 결과](#재학습-결과--1단계-복구-완료-2026-09-18) 참고.

## 모델

```
Conv2D(32, 3×3, relu) → MaxPool(2×2)
Conv2D(64, 3×3, relu) → MaxPool(2×2)
Conv2D(128, 3×3, relu) → MaxPool(2×2)
Flatten → Dense(256, relu) → Dropout(0.5) → Dense(7, softmax)

optimizer=adam, loss=categorical_crossentropy, epochs=20
```

> | --- | --- |
> | val_loss 곡선 | 단조 감소가 아니라 **6개 에폭에서 상승**(8·12·14·16·18·19)하는 진동 곡선 |
> | 20에폭 최저값의 정체 | 1.1738 → 1.2112 → **1.2333** → 1.1655 — **두 에폭 상승 뒤의 반등** |

## 실패한 부분 — 이모지 변환 (그리고 원인 진단의 오류)

원래 구상은 학습한 모델을 **이모지 이미지**에도 적용해보는 것이었습니다.
이모지를 48×48 이미지로 변환하려 했으나 **결과물이 전부 흰 이미지**로 나왔습니다.

이전 README는 원인을 *"이모지 원본 이미지가 기업 자산(라이선스 소유물)이라 정제된 데이터셋을
구하기 어려웠다"* 로 적었습니다. **그러나 실제 코드를 보면 라이선스와 무관합니다.**

```python
for i, emoji in enumerate(selected_data):
    emoji_image = Image.new('RGB', (48, 48), color='white')   # 흰 배경 생성
    emoji_draw  = ImageDraw.Draw(emoji_image)                 # draw 객체 생성

    # ← 여기에 emoji_draw.text(...) 로 이모지를 그리는 코드가 없음

    emoji_image.save(f"{output_directory}/emoji_{i+1}.png")   # 흰 이미지 그대로 저장
```

`ImageDraw.Draw()` 객체를 만들기만 하고 **`draw.text()` 호출이 빠져 있습니다.**
이모지를 그리는 단계 자체가 없으니 흰 이미지가 나오는 것이 당연한 결과입니다.

→ 실제 원인은 **코드 누락**입니다. 라이선스는 별개 이슈입니다.

### 그리고 애초에 모델이 필요 없었습니다

이모지에 CNN을 돌려서 얻으려던 감정 레이블은 **`emoji_df.csv`의 `name` 칸에 이미 있었습니다.**

```
😠 angry face        😨 fearful face       😢 crying face
😐 neutral face      😲 astonished face    🤢 nauseated face
```

FER 7개 클래스의 이름이 그대로 들어 있습니다. 필요한 것은 모델이 아니라 **대응표**였습니다.

원본이 선택한 `iloc[0:105]`도 임의의 숫자가 아니었습니다. 105개가 전부 `face-` sub_group이고,
잘라낸 자리 뒤(105~118)는 🤬😈👿💀☠️ 와 💩🤡👹👺👻👽👾🤖 — 해골·악마·광대·유령·외계인·로봇처럼
**사람의 표정이 아닌 얼굴**이며, 119번부터는 고양이 얼굴(😺)이 시작됩니다.
즉 **사람 표정 이모지만 골라낸 선택**이었습니다.

**데이터를 고른 판단은 처음부터 옳았습니다. 갈린 것은 그 데이터를 쓰는 방법이었습니다.**

## 3단계 완성 — 감정 벡터에서 이모지로

### ① 감정 수치화는 이미 되어 있었습니다

2단계 "감정을 수치화한다"는 사실 1단계에서 끝나 있었습니다. 원본 추론 코드입니다.

```python
predictions = model.predict(img_array)                   # ← 7차원 확률 벡터
predicted_label = class_labels[np.argmax(predictions)]   # 최대값 위치만 꺼냄
confidence = predictions[0][np.argmax(predictions)]      # 최대값만 꺼냄
```

`predictions[0]`이 7개 클래스의 확률 벡터입니다. 그런데 코드는 `argmax`로 하나만 꺼내고
**나머지 6개를 버렸습니다.** 버려진 그 벡터가 바로 감정 수치화였고, 새로 만들 것이 없었습니다.

### ② 이모지 대응표 — 105개 중 54개

`name` 키워드로 매핑했습니다. `sub_group`은 FER 클래스와 경계가 맞지 않습니다
(`face-concerned` 27개가 sad·fearful·surprised 셋에 걸쳐 있고, `face-unwell` 12개는 대부분 감정이 아닙니다).

| 클래스 | 개수 | 예시 |
| --- | --- | --- |
| happy | 21 | 😀 😄 😁 🤣 😊 🥰 😎 |
| sad | 16 | 😢 😭 😞 🥺 ☹️ 😔 |
| fearful | 4 | 😨 😰 😧 😱 |
| surprised | 4 | 😮 😯 😲 😳 |
| neutral | 4 | 😐 😑 😶 🫥 |
| angry | 3 | 😠 😡 😤 |
| disgusted | 2 | 🤢 🤮 |

**51%(54/105)만 매핑됩니다. 이것은 실패가 아니라 결과입니다.**
나머지 51개는 FER 7개 클래스로 표현할 수 없습니다 — 감정이 아니거나(🤔 thinking, 😴 sleeping,
😷 medical mask), 7개 밖의 감정이거나(😏 smirking, 😒 unamused, 🙄 rolling eyes)입니다.
**이모지 목록이 7개 클래스 모델보다 표현력이 넓다**는 것이 원래 설계의 한계를 보여줍니다.

### ③ 매칭 규칙

1. 벡터의 최대 클래스를 고름
2. 그 클래스 안에서 **모델의 확신도와 이모지 강도가 가장 가까운** 것을 고름
   (강도는 이름의 수식어로 부여 — `slightly` 0.3 / 기본 0.6 / `loudly`·`beaming`·`enraged` 0.9)

확신도가 높으면 센 이모지(😁 🤣), 낮으면 약한 이모지(🙂)가 뽑힙니다.

| 입력 감정 벡터 (예시) | 최대 클래스 | 확신도 | 할당 |
| --- | --- | --- | --- |
| 아주 밝게 웃는 얼굴 | happy | 0.92 | 😁 |
| 화난 얼굴 | angry | 0.78 | 😡 |
| 우는 얼굴 | sad | 0.88 | 😭 |
| 놀란 얼굴 | surprised | 0.71 | 😮 |
| 무표정 | neutral | 0.64 | 🫥 |

> 위 벡터는 규칙 검증용으로 **손으로 지정한 값**입니다. 모델 출력이 아닙니다(2026-09-10 당시 가중치 소실 상태).

### ④ 이 파이프라인의 진짜 한계 — 확신도 0.28

원본이 실제 사진에 대해 낸 확신도는 **0.28**이었습니다. 7개 클래스에서 최대가 0.28이면

| 0.02 | 0.0% | — |
| 0.05 | 7.1% | — |
| 0.10 | **41.9%** | **0.0%** |

**확신도가 낮으면 할당 결과가 사실상 임의가 됩니다.** 이것은 매칭 규칙의 결함이 아니라

파인튜닝되지 않음)가 직접 이미지를 보고 7개 클래스로 분류한 것과 Run B CNN의 예측을
같은 표본·같은 정답으로 비교했습니다.

| | 정확도 (n=100) |
| --- | --- |
| Run B CNN (619k 파라미터, 이 데이터로 학습) | 0.650 |
| Claude 비전 (제로샷, 이 데이터를 학습한 적 없음) | 0.750 |

| 클래스 | 표본 수 | CNN | Claude |
| --- | --- | --- | --- |
| angry | 11 | 0.727 | 0.727 |

가장 큰 차이는 `sad`입니다 — CNN은 22장 중 7장만 맞혔고(0.318), 대부분을 `angry`나
`neutral`로 잘못 분류했습니다. CNN이 놓치고 Claude가 맞힌 사례들을 보면 다음과 같은
패턴이 있습니다 — `sad/im48.png`(찌푸린 노년 남성 → CNN: angry, Claude: sad), `sad/im587.png`·`sad/im653.png`
(고개 숙인 낙담한 표정 → CNN: neutral, Claude: sad), `sad/im548.png`(울음 직전의 아기 →
CNN: angry, Claude: sad). CNN이 `sad`를 미묘한 얼굴 근육 신호(처진 입꼬리, 아래로 향한 시선)
대신 더 뚜렷한 신호(찌푸림→angry, 무표정에 가까움→neutral)로 계속 오인하는 경향이 보입니다.

반대로 Claude가 틀리고 CNN이 맞힌 6건은 대부분 **모호한 표본**이었습니다 —
`happy/im513.png`·`happy/im796.png`(아기 얼굴/어두운 사진이라 표정 판독이 어려움),
`angry/im646.png`·`fearful/im661.png`(차분해 보이는 얼굴이라 사람이 봐도 애매함).

**해석**: `disgusted`는 표본이 1장뿐이라 결론을 낼 수 없습니다(`[미검증]`). 나머지 6개
클래스로 좁혀 봐도, 100장은 정확한 정확도를 확정하기엔 작은 표본입니다 — 이 수치들은
"어느 쪽이 이겼다"를 선언하기보다 **방향성**으로 읽어야 합니다: 학습되지 않은 범용 비전
모델이 이 좁은 과제에 특화 학습된 619k 파라미터 CNN과 최소 동급이거나 더 나은 경향을
보였고, 특히 미묘한 표정(`sad`)에서 격차가 두드러졌습니다. FER 계열 데이터셋은 애초에
사람 채점자 간 일치율도 65~68% 수준으로 알려져 있어(라벨 자체의 주관성), 두 모델 다
이 상한 근처에서 움직이고 있다는 점도 함께 봐야 합니다.

**이게 "최종 목표를 LLM으로 완수한다"는 뜻은 아닙니다.** 이 프로젝트의 최종 목표(사진→감정→이모지)를
실제로 LLM 호출로 대체하려면 API 키·비용·네트워크 의존성이 필요하고, 이번 비교는 그 타당성을
가늠해본 참고 자료일 뿐 실제 파이프라인 교체는 하지 않았습니다. 산출물: `retrain_artifacts/llm_vs_cnn_100.csv`
(100장 각각의 정답·CNN 예측·Claude 예측·판단 근거).

## 이모지 매칭 파이프라인을 실제 사진 100장으로 실행 (2026-09-18)

`이모지_매칭_파이프라인.ipynb`(§6 `assign_emoji`)는 완성 당시 1단계 가중치가 없어서
**"손으로 지정한 예시 벡터"**로만 검증됐었습니다. 재학습(Run B)으로 진짜 가중치가 생겼으니,
같은 매칭 규칙을 위 CNN-vs-Claude 비교에 썼던 **실제 사진 100장**에 그대로 적용해봤습니다 —
`이모지_매칭_100장_실사진.ipynb`(생성기: `build/build_emoji_matching_100.py`)에 실행 결과로 남아 있습니다.

| 입력 | 이모지의 클래스 정확도 | 비고 |
| --- | --- | --- |
| CNN(Run B)의 실제 softmax 벡터 | 0.650 | 진짜 확신도 포함 — 매칭 규칙의 강도 선택이 실제로 작동 |
| Claude의 예측 라벨 | 0.750 | 확신도가 없어 매칭표 기본 강도(0.6)로 클래스만 룩업 |
| 둘의 최종 할당 이모지가 일치하는 비율 | 0.440 | 클래스 정확도 차이보다 낮음 — 서로 다른 사진에서 서로 다르게 틀림 |

"클래스 정확도"는 위 CNN-vs-Claude 벤치마크와 같은 수치입니다 — 매칭 규칙은 클래스를
바꾸지 않고 그 안에서 강도(이모지 세기)만 고르기 때문입니다. **여기서 새로 확인한 것은
숫자가 아니라 사실 자체입니다**: 3년간 "1단계 가중치만 복구하면 완결"이라던 조건부 문장이
오늘 실제로 채워졌고, 사진 → CNN → 감정 벡터 → 이모지가 예시가 아니라 **진짜 데이터
100장으로 실제로 동작**하는 것을 확인했습니다. 다만 품질은 여전히 1단계 CNN(정확도 0.5954)이
정한 상한 그대로입니다 — 100장 중 약 35장은 애초에 틀린 클래스로 이모지가 배정됩니다.

## 배운 점

- **"코드가 에러 없이 돌았다"와 "결과가 올바르다"는 다릅니다.** 이모지 변환은 예외 하나 없이
  완료됐지만 산출물은 전부 흰 이미지였습니다. 중간 산출물을 눈으로 확인하는 단계가 없으면
  이런 실패는 마지막에야 드러납니다.
- **실패 원인을 잘못 진단하면 잘못된 교훈이 남습니다.** "라이선스 문제였다"고 정리해두면
  다음에도 같은 코드 실수를 반복하게 됩니다. 원인은 코드에서 확인해야 합니다.
- **문서가 프로젝트를 실제보다 낮게 평가할 수도 있습니다.** 이 README를 정정하기 전까지
  완성된 모델이 "실패 사례"로 기록되어 있었습니다.
- **곡선의 마지막 한 점으로 수렴을 판단하면 안 됩니다.** "val_loss가 마지막 에폭에서 최저"는
  사실이지만, 그 앞 두 에폭이 상승 중이었다는 것을 빼고 말하면 **정반대 결론**이 나옵니다.
  추세는 점이 아니라 구간으로 봐야 합니다.
- **학습이 끝난 모델은 저장해야 존재합니다.** `model.save()` 한 줄이 없어서
  22,968장으로 약 18분간 학습한 결과가 남지 않았습니다.
- **버그를 고치는 것과 실험이 성립하는 것은 다른 문제입니다.** `draw.text()` 누락은 진짜 버그였고
  실제로 고쳤지만, 고치고 나서 보니 **사람 얼굴로 학습한 모델을 이모지에 적용한다는 발상 자체가
  성립하지 않았습니다.** 당시에는 코드가 막혀서 이 지점까지 오지 못했습니다.
- **모델을 붙이기 전에 데이터에 답이 있는지 봅니다.** 이모지 감정 분류는 CNN·GPU·학습 데이터가
  필요한 문제처럼 보였지만, 실제로는 **CSV 한 칸을 읽는 문제**였습니다.
  가장 비싼 해법부터 떠올린 것이 3단계에서 막힌 진짜 원인이었습니다.
- **형식이 같다고 같은 데이터가 아닙니다.** 48×48 그레이스케일이라는 형식이 맞는지가 아니라
  **분포가 맞는지**를 봐야 했습니다.
- **파이프라인의 품질은 가장 약한 단계가 정합니다.** 3단계 매칭 규칙을 아무리 정교하게 만들어도
  1단계 확신도가 0.28이면 결과는 임의에 가깝습니다. 공들일 곳은 뒤가 아니라 앞이었습니다.
- **중간 산출물을 버리지 않습니다.** `argmax` 한 줄이 7차원 벡터를 숫자 1개로 줄였고,
  그래서 2단계를 "새로 해야 할 일"로 착각했습니다.
- **generator가 몇 장을 읽었는지 확인합니다.** `validation_split`이 두 디렉터리에 걸쳐 적용되면서
  훈련·평가 양쪽에서 약 5,700장씩 조용히 빠져나갔습니다. `flow_from_directory`는 읽은 장수를
  출력하는데, 그 숫자를 데이터셋 크기로 믿고 README에까지 옮겨 적었습니다.
  **출력된 숫자가 의도한 숫자인지 대조하는 단계**가 없었습니다.
- **에러 없이 도는 코드가 가장 위험합니다.** 흰 이모지 이미지도, 5,700장씩 사라진 학습도,
  `argmax`가 7차원 벡터에서 6개를 버린 것도 — 이 프로젝트에서 발견한 문제 셋이
  전부 **예외 하나 없이 완료된 코드**에서 나왔습니다.
- **"예시로 검증됨"과 "실행됨"은 다릅니다.** 매칭 규칙(§6)은 손으로 만든 벡터 6개로는 이미 검증돼
  있었지만, 그게 "파이프라인이 완성됐다"는 뜻은 아니었습니다. 진짜 사진 100장을 진짜 CNN에
  통과시키고 나서야 "3단계는 완성, 1단계만 복구하면 끝"이라는 3년 묵은 조건부 문장이 실제로
  참인지 확인할 수 있었습니다.
